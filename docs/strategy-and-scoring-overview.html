1这是什么策略

一句话：以 BTC 为基准、带风险预算、多因子的 Core–Satellite（核心—卫星）中周期现货配置策略。 它只在证据足以支撑该资产特有的风险时才去追求超额收益；证据不够或时机不好时，资金可以留在稳定币/现金袖里。

它是什么

  • 按 3–6 个月视野做主动配置
  • 组合层面管理风险，不按单资产各自管
  • 分数 → 置信度 → 状态 → 闸门 → 上限 → 再平衡 → 分批，逐层收敛
  • 确定性计算全部由 Python 拥有；语言模型只能做有边界的语义判断

它明确不是什么

  • 不是日内/高频交易，不是纯动量趋势跟踪
  • 不是无脑定投抄底，也不是市值加权固定配置
  • 不用高质押年化去为弱资产背书
  • 不碰合约、永续、杠杆、保证金、杠杆代币
  • 不接交易密钥，不自动下单
BTC 的双重身份。它既是对标基准，也是风险资本的默认「机会成本资产」。 所以任何 ETH 或卫星的加仓都必须回答一个问题：「为什么是加它，而不是加 BTC？」 正绝对收益不够，如果同样的钱放在 BTC 上有更好的风险调整回报，那就不该加。 另一方面，BTC 没有自动分数加成，也不是不能减配——它有自己的一套趋势、估值、流量、宏观、事件与链健康风险。

事件状态从 ELEVATED 升到 HIGH（新风险倍数 0.75 → 0.50）会压缩部署额度。 但「压缩到哪一层」对卫星和核心并不一样，这是全篇最容易踩的一个例外：

核心
BTC / ETH		 锚 × 分数质量 × 置信度乘数 × 事件风险乘数（见 _allocate_core）。乘数直接烘进目标，核心没有独立的部署层。 没有单独的第二层可拦。事件或置信度一变，目标本身就跟着变小，越过再平衡带就可能直接产生减仓。
「临时部署限制不能单独生成 REDUCE」这句话只对卫星成立。 核心资产遇到 ELEVATED → HIGH 时，战略目标是会变小的——因为事件乘数和置信度乘数就写在核心目标的算式里 （raw = anchor × 分数质量 × confidence_multiplier × event_multiplier）。 这是已登记且已决定保留的行为，不是待修 bug：见 docs/PENDING_POLICY_DECISIONS.md 8B 的 F3 描述与「multipliers stay in core raw proportions」的裁定。 要改动它需要单独决策，不能靠观察顺手调整。
换句话记：卫星是两层结构（目标 / 允许），核心是一层结构（乘数都烘进目标）。 所以「一个临时的数据或事件波动最多只能拦住新增，不能逼你卖」这条保护， 目前只覆盖卫星。

3决策流水线：分数只是第三层

整条链路自上而下逐层收敛，每往下一层都只能「收紧」不能「放宽」。左侧是层的名字，右侧写清楚了这一层能把什么拦住。

4评分模型

基础分是 0–100 的确定性中周期吸引力度量。工具体系里有八个规范因子键，但每个资产用哪几个、权重多少，由 profile 决定。

4.1 三套权重 profile

默认 profile 六个正权重因子；BTC 与 AAVE 各有专用 profile。权重必须覆盖八个键且和为 1，否则加载即报错。零权重因子解析为 NOT_APPLICABLE（而非 MISSING），不计入分数与覆盖率。

4.2 八个因子逐个拆

八个规范因子键是一个固定集合：trend、valuation、fundamentals、onchain、capital_flows、relative_strength_btc、btc_valuation、macro_liquidity。每个 profile 必须恰好覆盖这八个键——多一个、少一个都在加载时直接报错。所以「某个 profile 不用某个因子」是靠把权重写成 0 来表达的，而不是删掉键；零权重解析为 NOT_APPLICABLE，既不计入分数，也不计入覆盖率。

先记住这条分界：八个因子里只有三个有「公式」。
  • 确定性打分（3 个）：trend、capital_flows、relative_strength_btc。只有这三个在 config/policy.json 里挂着 factor_rules 条目——它们是闭式算术，由 Python 直接算出 0–100，同一份输入必然得同一分，可复算、可审计。
  • 语义打分（5 个）：valuation、fundamentals、onchain、btc_valuation、macro_liquidity。Python 只把原始观测预处理成不可变事实（当前值 / 上期值 / 变化 / 趋势分类 / 覆盖率 / 新鲜度 / 来源 id），0–100 分与置信度由有界判断给出，且必须附上支持证据与反方证据的 id。置信度随后进入可靠性计算（见 4.3）。
所以下面五节要读的不是「公式」，而是它拿到哪些事实、边界在哪里。这也是 4.2 原先只拿趋势举例的原因：只有那三个画得出算式。

趋势因子的三个容易被忽略的细节。
  1. 成交量扣分要做确认。WEAK 量能必须连续 2 个已收盘日线都成立才扣分。写入一条弱读数不扣分，只报告「已确认几个收盘」。历史教训：某次单一弱量读数叠加一个勉强成立的 MA20 金叉，让趋势因子在一次评审里摆动 22 分。
  2. 「没有支撑区」不是缺数据。支撑结构被评估过、结果为空，是一个中性结论，不降低覆盖率。
  3. 技术回撤不算趋势分。回撤只在趋势事实里作为上下文可见，分值由 valuation 拥有——避免同一经济现象被计两次。

4.3 可靠性收缩与覆盖率门槛

缺失的正权重因子保持自己的权重不重新分配，而是把自己的原始分「向 50 收缩」。缺失数据永远不会被当成利多证据。

base_score = Σ profile_weight[f] × effective_factor_score[f]
coverage   = Σ profile_weight[f] × reliability[f]

权重是已解析的固定权重，不做重归一化。自定义权重也必须和为 1，否则被拒绝。

4.4 相对强度 vs BTC：一个数字、一道闸门

非 BTC 卫星的 30D/90D/180D 超额收益先做波动率调整，再映射到 0–100：

excess_h            = asset_return_h − btc_return_h
expected_horizon_vol = annualized_std(asset_daily_return − btc_daily_return) × sqrt(horizon_days / 365)
risk_adjusted_h     = excess_h / max(expected_horizon_vol, epsilon)

中性带 0.10、饱和点 1.00：带内视为中性 50，带外连续单调映射并在 0–100 截断。三个视野的权重是 20% / 40% / 40%——一个月暴涨不能压过 90D/180D 的确认。

相对强度读数含义允许的动作
≥ 50跑赢或中性允许增持
30 – 50中度弱于 BTC只持有/减仓，禁止新增风险
< 30确认显著弱于 BTC硬拦截，任何分数都不合格
「缺证据」和「证据为负」是两个相反方向的信号。非 BTC 卫星如果缺失 BTC 相对证据，结论是 HOLD_OR_REDUCE（不新增风险），而不是卖出；缺失因子只会把加权分拉向中性， 永远不能单独造成卫星退出。没有独立的负面证据（论点破裂、严重事件、确认的相对弱势、组合硬风险）， 一个证据不全的已持有卫星就停在 HOLD_OR_REDUCE，保持当前权重。

同一个相对信号只算一次。对 ETH，它既进基础分，又作为核心配置的机会成本闸门；但不会再被当成连续的仓位乘数用第二次。ETH 的 FDV/市值是 NOT_APPLICABLE，不能贡献正向估值证据。

4.5 资金流：两种明确分开的口径

口径适用算法
归一化流量 BTC、ETH 及其他资产 优先用比率：ETF 净流入 / ETF AUM，或交易所净流入 / 流通市值。分母拿不到就等于流量缺失，不会退化成绝对美元值替代。死区 |flow| ≤ 0.001（记 50 分），饱和 0.01；7D/30D 权限高于 1D 噪声。
BNB 供给变化分位 仅 BNB（无 BNB ETF） 把 BSC 稳定币供应量的变化绝对值放到自身 365 天历史里排位：s_h = 50 + 50 × sign(g_h) × p_h，7/30/90 天权重 0.2/0.4/0.4。零变化正好 50 分，负变化不可能超过 50 分。样本不足 180 个的视野视为未校准、不贡献分数。

结果里永远记录是哪一种方法算出来的；历史排位永远不会被发布成一个 normalized_flow 比率。

5从分数到目标权重

5.1 卫星目标曲线（全文第二重要的图）

卫星的战略仓位是一条连续的分段线性曲线，只由分数决定，与当前持有什么无关。这消除了一个历史缺陷：已持有的卫星跨过入场线时，目标反而从「保持现状」掉到 0%（曾经的 66.9 → 67.0 断崖）。

5.2 风险档与硬上限

risk_tier（normal / high_beta / high）把卫星的风险信封按比例切分：normal 拿满当期的卫星上限，high_beta / high 只拿一半。战略目标就是这个信封内曲线算出的值——满分刚好触到信封，任何更低的分数都严格在信封之下。

风险信封 = 当期卫星上限 × 风险档比例          # normal 1.0 / high_beta·high 0.5
战略目标 = 风险信封 × 曲线分数比例
硬暴露顶 = 风险信封 + hard_cap_buffer_pp(3.0pp) # 超出即触发 RISK_BUDGET_BREACH 减仓
区分两类越界：超出硬暴露顶会绕过普通再平衡带，直接强制减仓； 在缓冲区内的小幅超出仍然由普通 2/4/8pp 带治理。风险档是一个评估输入而非连续的波动率/贝塔估计—— 目前要么是政策默认 POLICY_DEFAULT，要么是人工声明 MANUAL_ASSESSMENT， 代码里还不会输出 DETERMINISTIC_ESTIMATE（见第 9 节 8G）。

核心袖：70/30 是先验，不是承诺

BTC/ETH 的 70/30 只用来构造风险核心袖的起点，最终比例还要经过 ETH 分数与置信度、ETH/BTC 机会成本、事件风险、链活跃度、regime、集中度、稳定币要求与组合上限。

6组合风险

6.1 市场状态 Regime

Regime 由 BTC 趋势、波动率、流量、市场宽度按权重合成，再有回撤地板兜底。它决定本期「可用多少风险预算」，与「资产好不好」完全无关。

状态切换有刹车

  • 不因为单一噪声指标切换状态；需要趋势/波动/流动性/宽度/事件多个维度相互印证。
  • 每次评审最多移动 1 档（regime_transitions.max_notches_per_review = 1）。从 DEFENSIVE 直接跳到（或跳回）CAPITAL_PRESERVATION 必须先经过一次中间档评审，避免一次噪声观察把稳定币袖来回旋转 35 个百分点。
  • 严重系统性事件与回撤地板不受这个限速约束，永远不会被延迟。

6.2 回撤阶梯：组合层面，不是单资产止损

压力测试只作诊断：stress_diagnostic 用 policy.json 里的固定情景（BTC −20%、ETH −30%、SOL −40%、AAVE −40%、BNB −35%）计算加权情景收益、逐资产贡献、相对峰值的预期回撤与剩余预算容量。当前它标记为 DIAGNOSTIC_ONLY——不会自己阻止或缩放目标（哪个情景成为硬约束仍是待决事项，见 8C）。它刻意不用概率预测的口吻，目的是暴露隐藏的集中度与贝塔。

绝对 > 4pp可主动再平衡（还须通过所有风险闸门）
绝对 > 8pp 或 相对 > 100%高优先级，除非有书面记录的临时战术偏离

7.2 分批与方向确认

  • 渐进修复缺口。普通配置修正一次评审最多修复剩余缺口的 50%，且不超过 4pp。这不是拖延：历史带决定什么时候走下一步。
  • 硬退出绕过分批。论点破裂、SEVERE/CRITICAL 事件、硬分数地板、风险预算击穿——这四类原因立即执行。
  • 方向反转要确认。如果一次阈值穿越会把某资产的可执行方向翻转（相对既有方向），动作先挂成 DIRECTION_CONFIRMATION 的 WAIT，直到新方向在 2 个不同日收盘上持续成立。同一天重复评审只算一次。
  • 决定性穿越不等待。超出阈值 2pp 以上的果断穿越立即执行；四条硬退出原因也永不等待。REDUCE → EXIT 始终是降风险方向，从不被这个门拦。
  • 不再做「小额修补交易」。低于阈值的修补交易被取消（8E），执行分期取代了一次性校正；未解决的约束会显式保留而不是被藏起来。

8置信度链

三层置信度按固定顺序计算，每层都有自己的分数、等级、理由、上限与证据 ID。缺失数据保持缺失；即使是 NORMAL 状态也不授予任何加仓许可。

置信度不是盈利概率。0.90 HIGH 的含义是「这个决策被证据强力支持」，不是「这笔记 90% 会赚钱」。分数同理：80 分不是 80% 的上涨概率。

记账与基准（高完整性逻辑，单列一节避免被忽略）

  • 外部现金流用单位化 NAV 处理，且约定「挂在这一张快照上的现金流发生在该快照估值之前」：pre_flow_nav = (snapshot_value − flow) / existing_units，之后 new_nav = snapshot_value / new_units。首张快照的外部现金流必须为 0。
  • 原始余额变化不是投资收益。已经披露但未结清的现金流会让 NAV 停在 PROVISIONAL，绝不会被猜成 FINAL。
  • 稳定币之间互换不是外部现金流，也不是市场盈亏：它保持 external_cash_flow = 0，通过 INTERNAL_REALLOCATION（用户/交易所确认）或 INFERRED_INTERNAL_REALLOCATION（快照中方向相反的稳定币变动配对，带推断置信度）归因，配不平的部分体现为换汇成本/滑点。
  • 持有资产的收益数据必须完整：某个持仓的收益缺失时，绝不对剩余权重重新归一化来假装完整。
  • 基准是业绩对标尺，不是目标配置。主基准是 100% BTC 买入持有，它是唯一计算超额收益的对手（超额收益 = 组合 NAV 收益 − 主基准收益）；次基准 70/30 BTC·ETH 买入持有只作参照，不参与超额收益计算。
  • 外部现金流按事件点摊进基准。主基准的入金全额进 BTC；次基准的入金 $70 进 BTC、$30 进 ETH。分摊之后不做日度再平衡，权重任其自然漂移。基准的初始规模被设成组合的首期价值——否则真实美元金额的出入金会把基准冲垮，并悄悄把 70/30 拉回锚定比例。
  • 组合与基准的评估期、现金流时点必须严格一致，不一致直接报错而不是给一个看似合理的数字。两边都用同一套现金流调整后的单位化 NAV，所以「跑赢 / 跑输」是同一口径下的可比结论。
  • 别把两个 70/30 混为一谈。benchmarks.secondary 的 70/30 是被动参照线（买着不动）；core_allocation.anchor 的 70/30 是主动构造核心袖的先验（会随分数、置信度、ETH/BTC 机会成本、事件风险、regime 变化）。数字相同，用途完全不同。

9不可动摇的边界与已知待决事项

9.1 架构红线

  • 确定性金融计算归 Python。语言模型不得重算或覆盖引擎已产出的分数、权重、金额、区段、动作与风险标记。报告只能解释已定稿的数值。
  • 不做兼容层。只支持最新的 policy / data 合同，不加别名、不加迁移；破坏性变更后本地生成状态需要手动重建，用户数据永不自动迁移或静默删除。
  • 不接交易。不引入交易所交易密钥、下单、合约、永续、杠杆、保证金、清算逻辑或自动交易。只读集成都需要显式请求。
  • 失败关闭。核心原则一句话：不确定性只会降低可执行性，永远不会被猜测抹平。NO_TRADE 是有效结论，不是系统错误。

9.2 不得凭观察改动的策略不变量

不变量为什么
趋势因子中性点 = 50，均线比较严格方向性（> 加、< 减、相等不加不减）历史 bug 把相等算成看多，让「无信息」读数变成 72/81；趋势是权重最大的因子，会系统性抬高所有分数

stress_scenario 必须覆盖全部 core + satellitepolicy 加载时校验；漏掉卫星会让 portfolio_stress 变成 UNAVAILABLE

10十句常见误读

常见说法实际契约
「80 分就是 80% 概率要涨」分数是证据强度排序，不是概率。置信度也不是盈利概率。
「分数 67 → 应买 67%」分数只通过曲线映射到卫星额度的比例（67 → 40%），再受限 regime 上限、风险档信封、集中度、稳定币下限。
「BTC/ETH 是 core，所以该持有」core 是分类，不是配置权利，没有分数保底。70/30 是先验，不是承诺。
「已经持有了，所以总得留着」沉没成本不参与前瞻判断。要问的是：「如果这笔钱现在是稳定币，我今天会主动买它而不是买 BTC 吗？」
「跌了很多可以抄底」BTC 相对强度弱 + 基本面弱 = 不新增配置，跌得多不构成理由。
「数据缺失，用中性值补上就行」缺失因子保留权重并向 50 收缩，覆盖率和置信度同时下降；缺失永远不会变成利多。
「某个指标转差，应该马上换仓」换仓要过 2/4/8pp 带、方向确认（2 个收盘）、集中度与全部闸门。一到两根噪声日线不足以反转中周期建议。
「事件风险高，应该清仓」SEVERE/CRITICAL 禁止新增风险，不等于自动清仓；现有敞口仍走论点、再平衡与组合风险规则。
「杠杆/永续只是执行细节」整个策略仅现货。合约、永续、杠杆、保证金越界即违反安全边界。
「没有交易机会，说明系统没跑完」NO_TRADE / WAIT / HOLD 是一等公民的成功结论。
